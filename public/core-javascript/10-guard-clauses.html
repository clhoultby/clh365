Guard Clauses

I really strongly advise using guard clauses. We have all seen code like this:

The old way

class OrderService {
  submit(order: Order): Receipt | null {
    if (order) {
      if (order.items.length > 0) {
        if (this.customer.isVerified) {
          if (order.total <= this.customer.creditLimit) {
            return this.gateway.charge(order);
          } else {
            this.log("over limit");
            return null;
          }
        } else {
          this.log("unverified");
          return null;
        }
      } else {
        return null;
      }
    }
    return null;
  }
}

Differentiating the failure handling from the happy path can be difficult. Working out what condition caused the code to enter the failure handling can be a nightmare as the condition that caused it can be no where near to the error handling.

The new way

export const submit = (order, customer, gateway, log) => {
  if (!order) {
    return null;
  }

  if (order.items.length === 0) {
    return null;
  }

  if (!customer.isVerified) {
    log("unverified");
    return null;
  }

  if (order.total > customer.creditLimit) {
    log("over limit");
    return null;
  }

  return gateway.charge(order);
};

Each rule is a single block that states the condition and its consequence together. The happy path is the last line, and not nested.

Note the inverted conditions. Test for the case you want to reject

so if (order.items.length > 0) becomes if (order.items.length === 0).

Guards over else


if (!user) {
  return "anonymous";
} else {
  return user.name;
}

// the first condition has already exited, 
//so the else is unnecessary
if (!user) {
  return "anonymous";
}

return user.name;

Guard Clauses in Loops

Apply the same for loops, where continue is the guard:

export const activeEmails = (users) => {
  const result = [];

  for (const user of users) {
    if (!user.isActive) {
      continue;
    }

    if (!user.email) {
      continue;
    }

    result.push(user.email);
  }

  return result;
};

Guards also give you somewhere obvious to put comments describing why a condition is bad and potentially also throw. Every backend developer will have been told to validate their inputs, we should do the same.
